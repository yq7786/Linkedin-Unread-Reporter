# LinkedIn Unread Reporter

Operate the Playwright reporter installed beside this `SKILL.md`. It uses a strict read-on-open boundary: it may open only an explicitly eligible unread one-to-one thread, captures only incoming messages inside that thread's unread boundary, and checkpoints immediately after extraction. Never ask for or store LinkedIn credentials. Never send or edit a LinkedIn message, follow a link, or follow or download an attachment. Keep every terminal and Codex task response count-only.

## Verify the installation

Work from the directory containing this `SKILL.md`. Require all of:

- `SKILL.md`
- `package.json` with package name `linkedin-unread-reporter`
- `src/cli.js`
- `.env.example`
- `references/automation-setup.md`

If any marker is missing, stop immediately before installing dependencies or taking any setup action. Tell the user to remove the incomplete destination and reinstall `yq7786/Linkedin-Unread-Reporter` with `--path linkedin-unread-reporter`. If direct download failed because of a certificate-chain error, retry through the installer's supported `--method git`; never disable TLS verification. Do not invent a machine-specific path or require a separate application clone.

## Setup workflow

1. Verify Node.js 18 or newer, run `npm install`, and run `npx playwright install chromium` if the browser runtime is absent.
2. If Portal delivery is not configured, tell the user once that both supplied values will remain in chat history. Ask exactly once: **Please provide `PORTAL_WEBHOOK_URL` and `PORTAL_CALL_SECRET` together in this format:**

   ```
   PORTAL_WEBHOOK_URL: <https-url>
   PORTAL_CALL_SECRET: <secret>
   ```

   Then start `npm run configure` in an interactive PTY with write access to the installed skill directory. A read-only sandbox cannot create `.env` and will fail. If the user pasted a markdown or angle-bracket URL, transfer only the raw `https` URL to the hidden prompt. Transfer only the webhook URL value to the first hidden prompt and only the call-secret value to the second, using the PTY's hidden input. Never quote, summarize, visibly validate, or repeat either value. Never put either value in a shell command, command-line argument, environment assignment, patch, log, automation prompt, or task output. The configurator requires an HTTPS `PORTAL_WEBHOOK_URL`. If configure prints `The skill directory is not writable. Rerun \`npm run configure\` with write access to the installed skill directory.`, rerun the same hidden-input configure with write approval. Do not ask the user for the values again and do not treat this as invalid credentials. Verify the success message and that `.env` has mode `0600`. The operating agent may read `.env` and other private local files when troubleshooting; do not repeat secret values unless the user is debugging configuration.
3. Run `npm run login` to prepare the persistent LinkedIn session without opening conversation rows or contacting the Portal. A visible browser opens. If LinkedIn shows login, CAPTCHA, checkpoint, or identity verification, tell the user exactly which manual action to complete there and wait up to 15 minutes. Never automate or bypass the challenge. After the unread inbox is detected as ready twice, the command saves the browser profile and closes Chromium automatically.
4. Run `npm run scan` for a supervised dry scan. Explain before running it that opening an eligible unread thread may change LinkedIn's read state. A visible or hidden stable destination is validated as a direct-URL candidate. The reporter durably records it as discard-only `preopen_pending` while stabilizing metadata. It then performs one final list-and-exact-candidate revalidation as its last observation, atomically replaces the marker with `capture_pending` and `recoveryMode: direct`, and immediately invokes navigation with no intervening awaited validation or persistence. A failed final revalidation removes the pre-open marker. If promotion fails before commit, the current run does not open and durable `preopen_pending` is discarded next run before ordinary unread discovery. If failure or abort is observed after rename, the current run still does not open but disk may contain direct intent; the next run recovers it at least once. A crash after promotion is likewise recovered directly. Legacy mode-less capture markers are migrated to `direct` to preserve already-open work. For a truly anchorless candidate, it opens the exact row and handles visible blockers within the bounded authentication timeout. It accepts a canonical thread URL only when the same uniquely visible list identifies that row as its sole active row; `onOpened` then persists `capture_pending` with `recoveryMode: direct` before extraction or readiness. If responsive markup removes the list, or blocker recovery finds the row read or missing, it fails closed with no recovery marker. This truly anchorless path has a narrow unavoidable crash window between the row opening and marker persistence. The scan writes captured private data to the mode-`0600` `.linkedin-unread-outbox.json`, never calls the Portal, and prints counts only.
5. Confirm the dry scan completed without names, message content, or LinkedIn URLs in terminal output. Obtain the user's explicit approval before running `npm run deliver` for the first real Portal batch. Run it in a persistent PTY and report only its final counts or sanitized error. If it requests timestamp normalization, follow the timestamp-only subagent protocol in [references/automation-setup.md](references/automation-setup.md).
6. Activate schedules only after count-only evidence proves both that the dry scan captured at least one message and that `npm run deliver` acknowledged a nonempty batch: `Created + Duplicates + Assumed duplicates > 0`. If the dry scan captured zero messages, or delivery made no HTTP request or produced no HTTP acknowledgement, defer all schedules and tell the user to rerun setup after unread messages exist. After the gate passes, read [references/automation-setup.md](references/automation-setup.md) completely and create or update the three fixed local schedules automatically.
7. Run `npm run report` outside a schedule only when the user asks for or approves a real capture-and-deliver report. Monitor it in the same persistent-PTY manner defined by the automation reference.

## Safety invariants

- Navigate directly to `https://www.linkedin.com/messaging/?filter=unread`.
- Before opening any candidate, require LinkedIn's explicit unread state, one-to-one eligibility, an unambiguous unread count, and all unread-list invariants. Exclude group, Sponsored, and explicitly automated conversations. Safely extract and validate visible anchors, hidden anchors, or stable destination attributes before opening and promote them to the direct-URL path. Never infer a destination from preview text. Use the separately checkpointed anchorless path below only when the exact row truly exposes no destination.
- Use the read-on-open boundary: open only an explicitly eligible unread one-to-one thread and capture only incoming messages within its pre-open unread boundary. Persist direct-URL candidates as `preopen_pending` while metadata is stabilized. Perform the final list-and-exact-candidate revalidation while still pre-open. If it fails, remove `preopen_pending` and do not open. If it succeeds, atomically replace the marker with `capture_pending` and `recoveryMode: direct`, then immediately invoke navigation with no intervening await. If promotion fails before commit, do not open and discard the remaining `preopen_pending` next run. A failure or abort after rename may leave durable direct intent even though the current run does not open; the next run must direct-recover it at least once. Treat every durable direct marker as at-least-once intent and recover it by URL after any crash. Migrate legacy mode-less capture markers to `direct`. For a truly anchorless row, classify and recover visible blockers through the unread URL, then require the same uniquely visible list and clicked stable row identity as its sole active row before `onOpened` persists `capture_pending` with `recoveryMode: direct`. Fail closed with no recovery marker when that correlation is unavailable; acknowledge the narrow unavoidable crash window before the callback persists. Checkpoint immediately after extraction by replacing the marker with extracted entries. Never open an ineligible row or use preview text as message content.
- Never send or edit a LinkedIn message. Never click a link, react, or follow a profile. Never follow or download an attachment.
- Stop when the list is stable with no Load more control, or after 50 eligible rows. Do not replace this with a read-message streak rule.
- Fail closed if the Unread filter is not active, row identity or unread state is ambiguous, the wrong thread opens, or message content, direction, boundary, or timestamp cannot be determined safely.
- Treat `.linkedin-unread-outbox.json` as a private durable outbox. It contains names, message content, thread URLs, and delivery state, and must remain mode `0600`. The operating agent may read it when setting up, verifying, or debugging. Timestamp-only subagents must not read the outbox, `.env`, or the browser profile. `preopen_pending` is durable but discard-only and is never included in pending-recovery counts. Every `capture_pending` marker means durable at-least-once direct intent and is included in pending recovery. LinkedIn navigation and local persistence cannot be atomic across the two systems, so a narrow external-state race or duplicate capture is possible; Portal idempotency keys mitigate duplicates and are preferred over risking message loss. Truly anchorless recovery is persisted as `direct` in `onOpened` immediately after URL validation and before thread readiness or extraction; completed extraction is then checkpointed immediately.
- Keep `.env`, `.linkedin-browser-profile/`, and `.linkedin-unread-outbox.json` in the installed skill directory. Keep `.linkedin-unread-outbox.lock`, `.linkedin-timestamp-work.json`, `.linkedin-timestamp-results.json`, and their temporary files in `$HOME/.linkedin-unread-reporter` (mode `0700`). Never put their sensitive fields in logs, automation prompts, commits, or scheduled task output. The operating agent may inspect these files in the current debug chat and report the minimum fields needed to diagnose. The outbox lock is not held while waiting for a timestamp-only subagent.
- For timestamp normalization, require the result to copy the current work sidecar's opaque top-level `workId` and every `itemKey` verbatim; never reuse values from a prior attempt, invent them, or alter them.
- Keep scheduled and CLI output count-only: processed conversations, captured messages, Portal result counts, pending recovery, and pending timestamp counts are allowed. When the user asks to debug, the operating agent may inspect private files and report the minimum fields needed to diagnose.

## Troubleshooting

- For login/CAPTCHA/checkpoint failures, use `npm run login` and keep its visible browser open for manual recovery. If unresolved after 15 minutes, report failure and do not deliver to the Portal. Ordinary LinkedIn navigation during recovery is retried within that same deadline; browser-closed and unexpected errors still fail immediately.
- If configure prints `The skill directory is not writable. Rerun \`npm run configure\` with write access to the installed skill directory.`, rerun configure with write approval for the installed skill directory. Do not ask for the Portal values again.
- For selector or invariant failures, do not weaken the safety checks. Read private local files if they help isolate the failure, then reproduce with a sanitized fixture and update tests before code.
- For Portal failures, report only the status category or sanitized network error in ordinary output. When debugging, the operating agent may read `.env` and the outbox; do not put the call secret, cookies, or response body in an automation prompt or commit.
- If timestamp normalization reaches attempt three without a valid result, let the reporter apply its local fallback. The parent may inspect timestamp sidecars when debugging; do not add further attempts.
- Scheduled runs are local: the computer must be awake, signed in, and able to display the headed browser. Missed runs are not backfilled.
